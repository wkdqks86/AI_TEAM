## 1. 자료 소스 — 어디서 찾나

| 위치 | 내용 |
|---|---|
| `C:\dev\course\` | 강사가 만든 강의안 (`course_*` 폴더별 과목) |
| `C:\dev\study\` | 직접 작성한 실습 노트 |
| `%LOCALAPPDATA%\LectureNotes\transcripts\` | STT **교정본** `YYYYMMDD_N.txt` + **원문** `_raw.txt` |
| `%LOCALAPPDATA%\LectureNotes\summaries\` | 위의 AI 요약본 `YYYYMMDD_N.md` |
| `%LOCALAPPDATA%\LectureNotes\materials\` | 앱에 첨부한 강의안 사본 |

### 규칙

- **파일명 번호는 교시가 아니다.** 앱 내부 강의 id다. 초기에는 교시와 같았으나 지금은 어긋난다. 교시는 강의 제목이나 `lecture_notes.db`의 `recorded_at`으로 확인한다.
- **`auto_YYYYMMDD_N_HHMM.wav`는 N교시의 두 번째 테이크다**(앱이 교시 중간에 재시작된 것). 따라서 **녹취 두 건이 한 교시에 대응할 수 있다.** 전반/후반은 두 녹취가 **문장 단위로 이어지는지**로 확정하고, 두 파일 사이의 시간 차는 **녹취 공백**이므로 자료 상태에 적는다 (10-07: 09:27\~09:33, 6분).
- ⚠️ **`transcripts/old/`도 같이 확인한다.** 정리를 마친 녹취를 `old/`로 옮기는 운영 때문에 **당일 녹취가 입력에서 조용히 빠질 수 있다.** 입력에 없는 것과 존재하지 않는 것은 다르다 (10-07: `164`가 실제로 빠졌다 — 의도한 제외였지만 확인 없이는 구분 불가).
- **번호 순서 ≠ 시간 순서.** 실제로 번호가 시간순이 아니었던 날이 있다(09-09 오후). 범위를 받으면 순서를 먼저 확인한다.
- **인용은 교정본(`.txt`) 기준.** `_raw.txt`에는 오인식이 그대로 남아 있다.
- ⚠️ **전체 탐색 금지.** `study/`, `course/` 아래에 `.venv`, `node_modules`가 섞여 있다. `Glob`·`Get-ChildItem -Recurse` 전체 탐색은 타임아웃 위험이 크다. **최상위부터 얕게 확인한 뒤 필요한 하위 폴더만** 조회한다.

### 강의안 찾는 순서

> ⚠️ **먼저 `study/`와 `course/`의 같은 파일을 크기·mtime으로 비교한다.** 동일하면 그 강의안은 **배포본 그대로**이고, 강사가 수업 중 친 코드는 **거기에 없다.** 그때는 녹취 + 개인노트로만 복원되고, 강의안에 저장된 셀 출력은 **그날 화면이 아니다** (10-07: 강의안은 2024년 244행, 수업은 2025-10\~2026-10 242행으로 데이터가 달랐다).

`course/`의 파일 날짜는 전부 압축을 푼 날(09-02)이라 **시간으로는 그날 자료를 알 수 없다.** 대신:

1. `study/`에서 **그날 수정된 `.ipynb`**를 찾는다 ← 여기엔 실제 작업 시각이 남는다
2. `study/ml/2. data preprocessing` ↔ `course_Machine_Learning/2. Data Preprocessing` 처럼 **폴더 구조가 미러링**되므로 대응 폴더를 찾는다
3. 녹취록에 실제로 나온 용어(`sigmoid`, `feature_importances_` 등)가 강의안에 있는지로 확정한다

> 한 폴더에 노트북이 8개여도 그날 다룬 건 2~3개뿐인 경우가 많다.

### 실제 수업 범위 판정

자료의 **정확성**과 **실제 수업 범위**는 별도로 판단한다.

- **실제 수업 범위는 녹취록을 최우선 기준으로 한다.**
- 커리큘럼은 관련 강의자료 후보를 찾기 위한 기준이지, 실제 진도를 확정하는 기준이 아니다.
- 강의자료나 실습 노트에 다음 진도 내용이 포함되어 있어도 **녹취에서 실제로 다루지 않았다면 그 날짜의 기술 페이지에 포함하지 않는다.**
- 반대로 커리큘럼보다 진도가 빠르게 진행되어 다음 단원을 실제로 다뤘다면 **녹취를 근거로 그 부분까지 포함한다.**
- 녹취에서 설명이 짧더라도 실제 코드 실행·실습 흔적·화면 결과가 확인되면 포함할 수 있다.
- 실제 수업 범위를 먼저 확정한 뒤, 세부 내용의 정확성은 **실행 코드/결과 → 개인 실습 → 강의안 → 녹취 문맥** 순으로 교차 검증한다.
- 녹취가 없는 날은 강의안·실습 기록으로 실제 범위를 추정하고, **녹취가 없었다는 사실을 명시한다.**
- 실제 수업에서 다루지 않은 후속 내용은 필요하면 `다음 진도 후보`로만 구분하고 날짜 페이지 본문에는 섞지 않는다.

### 🔴 소스를 추정하지 말 것

- **폴더·파일명만 보고 소스를 정하지 않는다.** 요약본 키워드(예: "킥스타트")로 실제 코드가 든 파일을 검색해서 찾는다.
- **사용자가 지정한 폴더와 실제 내용이 다를 수 있다.** 페이지에 이미 있는 이미지·메모를 먼저 역추적해 진짜 출처를 찾는다(09-02에 실제로 어긋났다).
- **녹취의 고유명사가 코드의 문자열 인자일 수 있다.** 회사명·서비스명은 **대상이 아니라 도구**일 수 있다. 녹취에 나온 이름을 **코드에서 문자열로 검색**해 함수 인자 자리인지 본다 (10-07: 녹취의 "네이버"는 종목이 아니라 `web.DataReader("005930", "naver", ...)`의 데이터 소스였고, 종목은 삼성전자였다). **사용자 노트의 주석도 같은 오류를 물려받는다.**
- **코드 기반 정리는 녹취보다 코드 주석이 먼저다.** 사용자가 직접 쓴 주석은 그 사람이 이해한 방식 그대로라 교재로 쓰기에 가장 좋다.
- 녹취가 깨진 구간은 **노트 코드가 1차 자료**다. 단 **"누가 쓴 코드인지"**(강사 공유 vs 내 풀이)를 먼저 가른다 — 파일명 `_tech`, 녹취의 "디스코드에 드린" 같은 단서를 본다.

### 그룹 페이지 6개 — linked view로 자동 채움

영역별 목록 페이지다. **손으로 링크를 나열하지 않는다** — 각 페이지에 `FILTER "영역" = "<값>"` 인 **linked list view**를 심어 새 강의가 자동으로 올라오게 한다.

> **"목록을 만들어달라"는 요청은 대부분 linked view가 정답이다.** 손으로 나열한 목록은 만드는 순간부터 낡기 시작한다.

### 새 날짜 페이지 만드는 법

`notion-create-pages`의 부모를 **data_source_id**로 지정한다.

```json
{
  "parent": {"type": "data_source_id", "data_source_id": "102b0c93-76fe-48ee-af60-b56a9a76592b"},
  "properties": {
    "제목": "2026-09-11 ○○ 정리",
    "date:날짜:start": "2026-09-11",
    "영역": "지도학습",
    "주제": ["모델평가", "경진대회"],
    "강의안": "study/ml/..."
  }
}
```

- 날짜 키는 `날짜`가 아니라 **`date:날짜:start`**
- `주제`·`영역` 값은 **정의된 옵션과 정확히 일치**해야 한다. 오타는 400 에러(`앙상블`→`앵상블`로 1회 실패). 가운뎃점은 `·`(U+00B7)
- 새 태그가 필요하면 먼저 §10의 **멀티셀렉트 추가 절차**를 따른다
- DB 밖 페이지를 만들 때 `parent`는 `{"url": ...}`가 아니라 **`{"type":"page_id","page_id":"..."}`**

### 제목 네이밍

`YYYY-MM-DD 주제 정리`. 날짜 범위는 `YYYY-MM-DD~DD`이고 Notion에서 `~`는 `\~`로 이스케이프된다.

### "내 노트 점검" 섹션

사용자가 직접 쓴 노트의 **에러가 안 나는 결함**을 적는다. 에러가 나는 건 이미 알고 있으니 가치가 없다.

- 🟠 빨강 콜아웃 = 조용히 틀린 결과를 만드는 것 (전역 변수 참조, 라벨 순서 미보장, K-Fold 누수)
- 🟡 노랑 = 지금은 우연히 맞지만 환경이 바뀌면 깨지는 것
- ✅ 초록 = **잘한 것.** 반드시 넣는다. shape 주석, 규칙을 코드 위에 박아둔 것 등

### 오늘의 응용문제 (토글)


## 4. 기술 페이지 vs 커리어 허브 — 분배 규칙

| 내용 | 목적지 |
|---|---|
| 개념·코드·실습 | 날짜별 기술 페이지 |
| 실무 조언·커리어·마인드셋·업종 선택 | **커리어 허브** |
| 날짜에 안 묶이는 주제 (모듈화·설계) | **상시 참고 페이지** |

- 판단 기준: **"3주 뒤에도 이걸 다시 열어볼까?"** → 그렇다면 날짜 페이지에만 묻어두지 않는다.
- 커리어 허브의 각 항목에는 **`**출처**: YYYY-MM-DD OO 강의 중`** 한 줄을 반드시 남긴다.
- 기존 4개 카테고리에 안 맞는 묶음이 쌓이면 **새 하위 페이지를 만든다**(그렇게 AI 커리어 지형이 생겼다).

### 강사 이야기 이중 보존 원칙

강사 이야기는 날짜 페이지와 커리어 허브 중 하나를 고르는 문제가 아니다. **맥락과 재사용 목적이 다르면 두 곳에 서로 다른 형태로 남긴다.**

1. **수업 맥락이 있어야 뜻이 살아나는 발언**은 날짜 페이지 `강사 이야기`에 남긴다.
   - 그날의 코드, 실습 결과, 오류, 디버깅 상황과 직접 연결된 설명
   - 왜 그 말이 나왔는지 모르면 의미가 줄어드는 발언
2. **6개월 뒤 기술 내용 없이 읽어도 가치가 있는 발언**은 `커리어 & 실무 인사이트` 허브에도 보낸다.
   - 실무 조언, 커리어, 학습 태도, 포트폴리오, 업종 선택, AI 활용 방식
3. 두 조건을 모두 만족하면 **이중 보존**한다.
   - 날짜 페이지: 수업 맥락이 보이도록 짧게 또는 원문 중심으로 남긴다.
   - 커리어 허브: 날짜와 무관하게 다시 읽을 수 있도록 주제 중심으로 재정리한다.
4. 같은 문장을 그대로 복제하지 않는다. **날짜 페이지는 "왜 나왔는가", 허브는 "다시 어떻게 쓸 것인가"를 담당한다.**
5. 날짜 페이지에서 허브로, 허브에서 날짜 페이지로 **양방향 링크**를 단다.
6. 허브 쪽에는 반드시 `출처: YYYY-MM-DD OO 강의 중`을 남긴다.

판단 질문은 두 개를 순서대로 사용한다.

> ① "왜 이 말이 나왔는지 알려면 그날 수업 맥락이 필요한가?" → Yes면 날짜 페이지에 남긴다.
> ② "6개월 뒤 이 말만 따로 읽어도 다시 쓸 가치가 있는가?" → Yes면 커리어 허브에도 보낸다.

### 🔴 커리어 허브는 09-09 ~ 10-01, 23일간 방치됐다 — 재발 방지 규칙

원인은 §28에 "다음에 커리어 허브를 손볼 때 함께 넣는 것으로 **보류**한다"고 쓰고 그 뒤 한 번도 돌아오지 않은 것이다. 보류 항목이 날짜 섹션 산문에 묻혀 추적되지 않았다.

1. **날짜별 정리를 마칠 때마다 "커리어 허브 반영분"을 명시적으로 적는다. 없으면 "없음"이라고 적는다.** 기록이 비어 있으면 *안 한 것*과 *할 게 없던 것*을 구분할 수 없다.
2. **"다음에 하겠다"로 미루지 않는다.** 미뤄야 하면 일지의 열린 작업 섹션에 **한 줄로 올린다.**
3. **"강사 이야기" 섹션만 보지 않는다. 본문을 읽는다.** 섹션이 없다는 것은 그날 커리어 내용이 없었다는 뜻이 아니라, 내가 그날 섹션을 안 만들었다는 뜻일 뿐이다. (실측: 섹션 없는 페이지 5개 중 **4개에 반영할 내용이 있었다.**)
4. 날짜 페이지의 "강사 이야기"를 쓸 때마다 **① 수업 맥락 보존이 필요한지 ② 장기 재사용 가치가 있어 허브에도 보낼지** 그 자리에서 판단한다. 둘 다 Yes면 이중 보존한다.

## 5. 원문 인용 기준

**형식(B안)**: STT 원문에서 반복·버벅임은 제거하되, **화자의 어투·비유·표현은 최대한 살린다.** 완전히 축약된 요약문으로 만들지 않는다.

### 무엇을 원문으로 남기나 — 3가지

1. **구체적 수치·기준**을 콕 집은 부분 — "실무 권장 5,000개 이상", "경진대회 10위 이내"
2. **강사의 실제 경험·일화** — "직원 13명 중 50%를 지인 추천으로 뽑았다"
3. **인상적인 비유·단정적 조언** — 제육볶음 비유, "자격증은 실력 증명이 아니다"

### 명백한 오인식은 고쳐서 인용한다

이 STT는 품질이 낮아 단순 반복 제거로 끝나지 않는다. "캐들"→캐글, "통공과"→전공자, "문상관"→수상경력 같은 **문맥상 명확한 오인식은 바로잡아 인용**하고, 어느 부분을 고쳤는지 따로 밝히지 않는다. 원문인 척 왜곡하는 것과 명백한 STT 오타를 고치는 것은 다르다.

### 복원 불가 구간

잡음이 심해 문장 복원이 불가능하면 인용을 포기하고 요약본 기준 paraphrase로 대체하고, 출처 줄에 **"(요약본 기준 정리)"** 라고 표시한다.

### 녹취가 없는 날

강의안·코드만으로 정리한다. 인용구·개인노트 없이 구성하면 된다 — 이 인용 기준은 애초에 녹취가 있을 때의 규칙이다.

### 강사와 내 판단이 다를 때

**둘 다 적는다.** 강사의 해석을 먼저 쓰고, 내 분석을 근거와 함께 병기한다(10-01 K-Fold: 강사는 "로컬 미니마 극복", 내 분석은 "데이터 누수").

## 6. 이미지 처리 — API 제약

> 모델 성능과 무관한 **Notion API의 구조적 제약**이라 항상 유효하다.

1. `notion-fetch`로 읽은 S3 이미지 URL(`...?X-Amz-...`)은 **매 요청마다 새로 서명되는 5분짜리 임시 URL**이다. 그 텍스트를 `update_content`의 `old_str`으로 써도 **매치되지 않는다**.
2. 🔴 **절대 presigned S3 URL을 `![]()` 에 직접 박지 말 것.** 5분간은 되는 것처럼 보이지만 이후 영구히 깨진다(실제로 1회 사고, 재업로드로 복구).
3. 이미지를 옮기거나 다른 페이지에 넣으려면:
   - fresh 서명 URL을 `curl`로 로컬에 다운로드
   - `notion-create-file-upload`로 슬롯 생성 → 반환된 `upload_url`/`upload_headers`로 `curl -F "file=@파일"` POST
   - 본문에 **`![alt](file-upload://<file_upload_id>)`** 로 삽입
3-1. ⚠️ **Git Bash에서 `curl -F "file=@..."`에 절대경로를 쓰면 실패한다**(exit 26). `cd`로 이미지 폴더에 들어간 뒤 **파일명만** 넘긴다. 업로드 응답의 `markdown_source`(`file-upload://<id>`)를 `![캡션](file-upload://<id>)` 형태로 본문에 넣고, 반영 뒤 `notion-fetch`로 **`notion-file-block://`으로 바뀌었는지** 확인한다 — 그게 presigned URL이 박히지 않았다는 증거다.
4. `replace_content`로 페이지를 통째로 재구성할 때는 **기존 이미지도 재다운로드→재업로드**해야 한다. 손대지 않는 이미지는 그대로 둬도 무방.
5. **Notion 통합에는 페이지 삭제 API가 없다.** 삭제가 필요하면 사용자에게 안내한다. **뷰도 API로 삭제할 수 없다.**
6. 노트북의 base64 인라인 이미지는 `Read`로 못 읽는다(3MB+). `scratchpad/nbdump.py`를 쓴다 — 정규식 `!\[[^\]]*\]\(data:image/[^)]{40,}\)` → `[이미지]`로 치환.

## 7. 태그 설계 원칙

> **영역 = 어디에 속하는가(하나) · 주제 = 무엇을 가로지르는가(여럿)**

**주제 태그는 영역 경계를 넘는 것만 만든다.** 영역 하나 안에서만 쓰이는 태그는 영역과 중복이라 가치가 없다.

| 태그 | 가로지르는 영역 |
|---|---|
| `모듈화` | 데이터 전처리 + 지도학습 → 🧱 모듈화 노트와 짝 |
| `수학·통계` | 분석 기초(선형대수) + 지도학습(경사하강·MLE) + 비지도(PCA) |
| `시각화` | 분석 기초(Seaborn) + 전처리(EDA) + 지도학습(ROC·SHAP) |
| `재현성` `경진대회` | 대회 실무용 가로축 |

> **하루에 노트북 두 권을 다루면 태그가 늘어난다.** "하루 = 한 주제"를 전제로 고르면 안 된다. **노트북 단위로 고른 뒤 합치고**, 5개를 넘어가면 페이지를 둘로 쪼갤지 먼저 검토한다 (10-07: 시계열 회귀 + 자연어 생성 → 5개).

**현재 주제 옵션 (16개)**: 전처리 · 시각화 · 수학·통계 · 회귀 · 분류 · 앙상블·부스팅 · 모델평가 · 오버피팅 · 하이퍼파라미터 · 모델해석 · 모듈화 · 재현성 · 경진대회 · 크롤링 · 협업·환경 · 자연어처리

> **태그가 대체 못 하는 것**: 태그는 "같은 주제다"까지만 말한다. "하이퍼파라미터 importance ≠ 피처 importance, 후자는 이쪽" 같은 **연결의 이유**는 못 담는다. → §8 관련 노트와 **둘 다** 유지한다.

## 8. 관련 노트 링크

모든 날짜 페이지 하단에 넣는다.

```markdown
---

### 🔗 관련 노트

- <mention-page url="https://app.notion.com/p/<id>"/> — 왜 연결되는지 한 줄
- ...

📚 전체 목록·주제 태그로 찾기 → [강의 노트 DB](https://app.notion.com/p/e92ee1d3029046ae8da54182226aef85)
```

- **마크다운 링크가 아니라 `<mention-page>`를 쓴다.** 페이지 제목이 바뀌면 표시도 따라 바뀐다.
- 한 줄 설명은 "왜 연결되는가"다. 제목 반복이 아니다.
- ⏩ 다음 수업, ✅ 그 질문의 답 같은 **방향 표시**를 붙이면 더 좋다.

### 규칙

- **새 페이지를 만들 때 `관련 노트`를 처음부터 넣는다.** 나중에 몰아서 하면 전체를 다시 훑어야 한다(실제로 28장을 한 번에 했다).
- **역방향도 그날 바로 건다.** 앞 페이지에 "이건 나중에 뒤집힌다"를 심을 수 있는 건 그때뿐이다.

## 8.5. 자료 상태와 Notion 반영 승인 규칙

### 자료 상태 — 중간 스냅샷과 최종 정리를 구분한다

같은 날짜라도 수업 중에는 녹취 파일이 계속 추가될 수 있고,
강사가 실습 노트북을 실행하면서 코드를 수정하거나 다시 배포할 수 있다.

따라서 **수업 진행 중 생성한 `claude_input`은 최종본이 아니라 스냅샷**으로 본다.

- 수업 중 작성본 / 최종 여부 불명
  - 코드 결함을 확정하지 않는다.
  - `재검증 필요`로 표시한다.
  - 강사의 의도인지, 미완성 코드인지, 실제 결함인지 구분하지 못한 상태로 남긴다.
- 수업 종료 + 최종 노트북 확인
  - 같은 날짜 자료를 다시 수집한다.
  - 이전 지적을 다음 5가지로 다시 분류한다.
    - `해결`
    - `유지`
    - `새 발견`
    - `강사 의도`
    - `강사 관행`
    - `확인 필요`

### 최종 정리 시점

최종 Notion 정리는 다음 조건이 충족된 뒤 진행한다.

1. 해당 날짜 녹취가 더 이상 추가되지 않는 상태
2. 강의/실습 노트북이 최종 상태인지 확인
3. 같은 날짜 `claude_input`을 다시 생성
4. 이전 스냅샷의 지적을 재검증

수업 시간(예: 09:00~17:50)은 **현재 자동화 코드의 판별 조건으로 넣지 않는다.**
현재 흐름은 사용자가 수업 종료 후 직접 실행하는 방식이므로,
시간 조건보다 **실제 녹취/노트북의 완료 상태**가 더 중요하다.

### A~G 산출물의 Notion 반영 위치

| 블록 | 역할 | 반영 방식 |
|---|---|---|
| **A. 날짜별 기술 페이지 본문** | 실제 강의 노트 본문 | 최종 검수 후 강의 노트 DB 본문에 반영 |
| **B. DB 속성** | 제목·날짜·영역·주제·강의안 | 최종 검수 후 해당 DB 속성에 반영 |
| **C. 커리어 허브 반영분** | 커리어/실무 재사용 지식 | **승인 후보**. 사용자 확인 후 허브에 반영 |
| **D. 상시 참고 페이지 반영분** | 날짜에 묶이지 않는 지식 | **승인 후보**. 기존 페이지 우선 검토 후 반영 |
| **E. 관련 노트 후보** | 선행·후속·짝·보완 연결 | **승인 후보**. 양방향 링크까지 확인 후 반영 |
| **F. 커버리지 검증 결과** | 누락 검사용 | 기본적으로 최종 날짜 페이지 본문에는 넣지 않음 |
| **G. 작업 일지 기록** | 새 규칙·예외·사고 | **승인 후보**. 실제 새 규칙만 기준서에 추가 |

### 승인 원칙

- **A/B**: 자료가 최종 상태라는 전제에서 검수 후 반영한다.
- **C/D/E/G**: 자동으로 바로 쓰지 않는다. **후보 → 사용자 확인 → 반영** 순서다.
- **F**: 작업 품질 검수용이다. 최종 지식 페이지에 그대로 노출하지 않는다.
- 같은 날짜를 재실행한 경우, 이전 결과를 누적해서 붙이지 말고 **새 최종 입력 기준으로 재판단**한다.
- 이전 지적이 해결됐다면 삭제하거나 `해결`로 이동한다. 과거 오판을 새 문서에 그대로 남기지 않는다.

## 9. 표준 절차 — 하루 정리 체크리스트

```
[ ] 0. 자료 상태 확인 — 녹취 추가 중인지, 노트북이 최종본인지 확인. 불명확하면 '중간 스냅샷'
       ↳ `transcripts/old/`에 같은 날짜 파일이 있는지 / 강의안이 `course/` 사본과 동일한지 같이 본다
[ ] 1. 범위 확인 — 녹취를 기준으로 그날 실제 수업 시작·종료 범위와 다룬 주제를 확정
       ↳ 커리큘럼보다 빠르거나 느린 진도가 있으면 실제 녹취를 우선
       ↳ 녹취 파일 번호가 시간순인지 확인(번호 ≠ 교시 ≠ 순서)
[ ] 2. 소스 확정 — 확정된 실제 수업 범위에 해당하는 study/course 자료를 찾고 코드·실행 결과로 내용 검증
[ ] 3. 강사가 명시한 우선순위 확인 — "이건 핵심", "이건 참고용"을 먼저 찾는다
[ ] 4. 본문 작성 — §3 구조대로
[ ] 5. 내 노트 점검 — 에러 안 나는 결함 + 잘한 것
[ ] 6. 이미지 — §6 절차 (다운로드 → 재업로드 → file-upload://)
[ ] 7. ★ 녹취 커버리지 검증 패스 (아래)
[ ] 8. 커리어 허브 반영 후보 — 반영분을 적는다. 없으면 "없음". 자동 반영하지 않는다
[ ] 9. 관련 노트 + 역방향 링크 후보 — 사용자 승인 후 반영
[ ] 10. 일지(NOTION_정리_기준서.md) 후보 기록 — 실제 새 규칙만 승인 후 추가
```

### ★ 7단계 — 녹취 커버리지 검증 패스

슬라이드 위주로 정리하면 **슬라이드에 걸리지 않는 발화**(잡담, 부연설명, 실무 팁)가 누락된다. 페이지를 마무리하기 직전에 수행한다.

1. 초안을 다 쓴 뒤 그날 녹취록 **원문을 처음부터 끝까지 다시 훑는다**
2. 문단·발화 단위로 **"이 내용이 최종 정리본 어디에 반영됐는가"**를 확인한다
3. 반영 안 된 것을 찾으면:
   - 기술적으로 유의미 → **날짜 페이지에 섹션 추가**
   - 실무·커리어성 → **커리어 허브에 섹션 추가**
   - 사소한 반복·잡담 → 의도적 제외로 판단하고 넘어간다
4. 이 패스를 거쳤다는 사실과 결과(누락 발견 여부)를 **일지에 한 줄 남긴다**

> **한계**: 원문(`transcripts/`)이 있는 날에만 완전히 적용된다. 요약본만 있는 날은 효과가 제한적이지만 같은 절차를 요약본 대상으로 수행한다. 녹취 자체가 없는 날은 적용 대상이 아니다.

### 긴 수집 작업은 중간 저장

여러 페이지를 훑어 내용을 모을 때는 **`scratchpad/`에 수집 결과를 중간 저장한다.** context 유실을 막는다(커리어 허브 복구 때 `career_hub_수집.md`로 12개 페이지 분량을 살렸다).

## 10. 도구 사용 시 주의

### 🔴 실제로 사고가 난 것들

| 사고 | 규칙 |
|---|---|
| MCP 서버 ID를 기억으로 쓰다 2회 실패 (`bae685ca84ae` → `bae605`, `bae85`) | **긴 서버 ID는 ToolSearch로 정확한 이름을 받아서 쓴다.** 눈으로 세면 틀린다 |
| 한글 유니코드 이스케이프 오타 2회 (`\ubd84\ub8e8`=분루 vs `\ubd84\ub958`=분류) | **한글 값은 이스케이프 대신 직접 입력한다** |
| `update_content` old_str 매치 실패 다수 (컬럼→컴럼, 쓸모→쎌모) | **`old_str`은 직전 `notion-fetch` 결과에서 그대로 복사한다.** 손으로 재입력하지 않는다. 실패하면 **받침 하나 차이**부터 의심한다 |
| `old_str`에 `<mention-page/>` 를 넣어 매치 실패 | **mention 마크업은 old_str에 쓰지 않는다.** 뒤따르는 평문만 앵커로 쓴다 (new_str의 mention은 정상 동작) |
| `replace_content`에 `content` 파라미터를 씀 | `replace_content`는 **`new_str`** 이다 |
| `notion-fetch` 출력이 너무 커서 인라인 반환 실패 | Notion이 저장 경로를 주므로 **Python으로 문자 범위를 잘라** 확인한다 |
| 공개 Notion 사이트(`*.notion.site`)를 WebFetch로 읽으려 함 | **JS 렌더링이라 본문이 안 온다.** 날짜 페이지 본문은 `notion-fetch`로만 읽힌다 |

### 멀티셀렉트 옵션 추가 절차

`ALTER COLUMN ... SET MULTI_SELECT(...)`는 **옵션 목록을 통째로 교체**한다. 따라서:

1. **DB를 fetch해 기존 옵션 전체와 색상을 먼저 확보**한다 (색을 빠뜨리면 바뀐다)
2. **현재 태그 사용 현황을 SQL로 덤프해 백업**한다 → `C:\dev\notion_backup\주제태그_백업_YYYYMMDD.md`
3. 기존 옵션을 **하나도 빠짐없이 같은 이름·같은 색으로** 나열하고 끝에 새 옵션을 붙여 `ALTER`
4. 실행 후 응답의 **옵션 URL(ID)이 변경 전과 같은지 확인** — 같으면 기존 페이지 값이 보존된 것
5. SQL로 `COUNT(*)`와 태그없음 건수를 변경 전후 비교

> 2026-10-01 `자연어처리` 추가 시 이 절차로 **손실 없음** 확인(42건 유지, 기존 15개 옵션 ID 전부 동일).

## 11. 판단 기준 모음

> 일지 전체에서 반복적으로 쓰인 판단 기준들.

| 질문 | 기준 |
|---|---|
| 날짜 페이지인가 상시 참고인가 | **"3주 뒤에도 이걸 다시 열어볼까?"** |
| DB인가 단독 페이지인가 | **반복되는 것은 DB, 하나뿐인 문서는 페이지** |
| 주제 태그를 만들까 | **영역 경계를 넘는가.** 안 넘으면 영역과 중복 |
| 목록을 손으로 만들까 | **거의 항상 linked view.** 손 목록은 만드는 순간부터 낡는다 |
| "강의안 보고 보강해줘"의 범위 | **강의안 전체를 옮기라는 뜻이 아니다.** 페이지의 "나중에", "주의" 같은 **열린 문장**을 먼저 찾고, 그 답이 강의안에 있을 때만 넣는다. 그래야 페이지가 강의안 사본이 되지 않는다 |
| 구조 변경을 제안할까 | **"지금 병목이 무엇인가"를 먼저 확인한다.** 이득을 과장하지 않는다. 다만 **마이그레이션 비용은 항목 수에 비례**하므로 할 거면 일찍 |
| 수치 결과가 유효한가 | **베이스라인과 비교한다.** 정확도 0.581은 다수 클래스 0.686보다 낮으므로 "아무것도 못 찾았다"가 맞다. `ln(10)=2.303` 같은 이론값 대조도 같은 종류 |
| fold 성적이 단조 감소하면 | **모델 생성 위치를 먼저 본다.** 정상 K-Fold는 fold 성적이 서로 비슷하다 |
| fold 성적이 **소수점 끝까지 똑같으면** | **상태 객체가 공유된 것이다.** 모델·옵티마이저·EarlyStopper가 루프 **밖**에 있는지 본다. 반대 지문도 있다 — **CV 점수는 높은데 홀드아웃이 낮으면** 폴드 간 모델 재사용으로 뒤쪽 검증 데이터가 이미 학습된 것 |
| 루프가 의도대로 도는가 | **`tqdm` 진행바 줄 수를 센다.** loss 값이 없어도 **구조는 증명된다** — 폴드별 `train_step` 반복 횟수로 조기 중단을, 배치 수로 샘플 수를 역산한다 |
