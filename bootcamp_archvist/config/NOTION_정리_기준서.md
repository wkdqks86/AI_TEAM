### 태그 설계 원칙

**영역 = 어디에 속하는가(하나), 주제 = 무엇을 가로지르는가(여럿).**
주제 태그는 **영역 경계를 넘는 것만** 만든다. 영역 하나 안에서만 쓰이는 태그는 영역과 중복이라 가치가 없다.
- `모듈화` — 데이터 전처리 + 지도학습 → 🧱 파이썬 모듈화 노트와 짝
- `수학·통계` — 데이터 분석 기초(선형대수) + 지도학습(경사하강·MLE) + 비지도(PCA)
- `시각화` — 데이터 분석 기초(Seaborn) + 전처리(EDA) + 지도학습(ROC·SHAP)
- `재현성` `경진대회` — 대회 실무용 가로축

**태그가 대체 못 하는 것**: 페이지 하단의 `관련 노트` 링크. 태그는 "같은 주제다"까지만 말하고, "하이퍼파라미터 importance ≠ 피처 importance, 후자는 이쪽" 같은 **연결의 이유**는 못 담는다. 둘 다 유지한다.

## 2. Notion 페이지 구조 표준 ("09.01 스타일")

기존에 만들어둔 기준 페이지: **2026-09-01 EDA & Data Cleaning 정리** (`https://app.notion.com/p/3ce8fc09deb9808292e9c4a78362310e`)

날짜별 통합 정리 페이지는 아래 골격을 따른다:

```
> 강의안(...)과 실습 노트(...)를 바탕으로 정리했습니다.
## 0. 오늘 한눈에 보기
- 불릿 요약 5~6개
---
## 1~N. (주제별 섹션, 번호+제목)
  - 개념 설명, 표, 콜아웃
  - 관련 실습 코드 블록
  - 관련 캡처/다이어그램 이미지는 "그 개념을 설명하는 문단 바로 아래"에 배치 (문서 맨 위/맨 아래에 몰아두지 않는다)
  - 원본 학생 개인 메모는 삭제하지 않고 `> 개인 노트: ...` 인용구로 관련 이미지/섹션 옆에 보존
---
## 4. 핵심 함수 Cheat Sheet (표)
---
## 5. 연습 문제 (5문항, 힌트→정답 순, 코드 포함)
---
## 6. 다음 계획
```

페이지 제목 네이밍: `YYYY-MM-DD 주제 정리` (예: `2026-08-24 GitHub 팀 협업(PR) 정리`). 날짜 범위는 `YYYY-MM-DD~DD` 형식, Notion에서 `~`는 `\~`로 이스케이프됨.

각 날짜 페이지 하단에는 "오늘의 응용문제" 섹션을 추가하고, 정답은 **토글(펼쳐보기)**로 가린다:
```
## 오늘의 응용문제
<details>
<summary>Q1. 질문 전체를 summary 안에 넣는다?</summary>
	답변 (탭으로 들여쓰기)
</details>
<details>
<summary>Q2. 다음 질문?</summary>
	답변
</details>
```
> **중요**: 질문을 별도의 마크다운 번호 리스트(`1. 2. 3.`)로 만들고 그 뒤에 토글을 붙이면 **깨진다** (`<details>` 태그가 escape되어 리터럴 텍스트로 저장되고 번호도 1로 리셋됨 — 2026-09-02 오전에 처음 겪음). 반드시 **질문 문장 자체를 `<summary>` 안에 넣어서** 번호 리스트를 아예 안 쓰는 방식으로 만들어야 한다 (같은 날 오후에 이 방식으로 재시도해서 정상 동작 확인함). 번호는 "Q1.", "Q2..."처럼 summary 텍스트 안에 직접 타이핑한다.
> **2026-09-02 완료**: 과거에 `**정답:**` 볼드+들여쓰기 방식으로 되어 있던 날짜 페이지 12개(08-18~20, 08-21, 08-24 GitHub/Requests/Selenium, 08-26, 08-27~28, 08-28, 08-31 SSH/Seaborn, 09-01 EDA 병합본, 09-02 인코딩)를 모두 토글 방식으로 일괄 전환 완료. 이제 모든 날짜 페이지가 토글 형식으로 통일됨 — 앞으로 새로 만드는 페이지도 이 형식을 기본으로 적용.
> **주의(재발 방지)**: 이 전환 작업 중 `update_content`의 `old_str`을 손으로 다시 타이핑하다가 한글 유니코드 이스케이프(`\uXXXX`)를 잘못 계산해 "No matches found" 에러가 여러 번 발생했다 (예: 컬럼→컴럼, 왜도→왕도/왔도, 겹쳐→겹쳤, 나눴다고→나눴다고 오타). **한글이 포함된 `old_str`은 반드시 직전 `notion-fetch` 결과에서 그대로 복사해서 쓸 것 — 수동으로 `\uXXXX` 이스케이프를 계산하거나 기억에 의존해 재입력하지 말 것.** 매치 실패 시 자잘한 오타(특히 받침 하나 차이)부터 의심할 것.

## 3. Notion 이미지 처리 — 반드시 지킬 기술적 사실

이건 모델 성능과 무관한 **Notion API의 구조적 제약**이라 항상 유효하다.

1. `notion-fetch`로 읽은 이미지 URL(`https://prod-files-secure-....s3...amazonaws.com/...?X-Amz-...`)은 **매 요청마다 새로 서명되는 5분짜리 임시 URL**이다. 이 URL 텍스트를 그대로 복사해서 다른 페이지의 `update_content`(search-and-replace)에 `old_str`으로 써도 **매치가 안 된다** (`No matches found` 에러) — 저장된 원본과 텍스트가 다르기 때문.
2. 이미지를 다른 위치로 옮기거나 다른 페이지에 넣고 싶으면:
   - 그 이미지의 fresh 서명 URL을 `curl`로 로컬 파일에 다운로드
   - `notion-create-file-upload`로 업로드 슬롯 생성 → 반환된 `upload_url`/`upload_headers`로 `curl -F "file=@로컬파일"` POST
   - 페이지 본문에는 `<image src="file-upload://<file_upload_id>"></image>` 형식으로 삽입
   - **절대 presigned S3 URL을 `![]()`에 직접 박아넣지 말 것** — 5분 안에는 동작하는 것처럼 보이지만 이후 영구히 깨진다 (실제로 이 실수를 한 번 했고, 재업로드로 복구함).
3. `replace_content`/`insert_content`로 페이지를 통째로 재구성할 때도 기존 이미지 블록을 건드리려면 위 절차(다운로드→재업로드)를 거쳐야 안전하다. 손대지 않는 이미지는 그대로 둬도 무방(내부 참조가 유지됨).
4. Notion 통합에는 **페이지 삭제 API가 없다** (`notion-*` 도구 목록에 delete 없음). 삭제가 필요하면 사용자에게 직접 지우도록 안내할 것.

## 5. 원문 인용 기준 (B안 확정)

**형식**: STT 원문에서 반복/버벅임은 제거하되, 화자의 어투·비유·표현은 최대한 살린 "정리된 인용"으로 넣는다 (완전 축약된 요약문이 아님).

**무엇을 원문으로 남길지 판단 기준 3가지**:
1. 구체적 수치·기준을 콕 집은 부분 (예: "실무 권장 5,000개 이상", "경진대회 10위 이내")
2. 강사의 실제 경험/일화 (예: "직원 13명 중 50%를 지인 추천으로 뽑았다")
3. 인상적인 비유·단정적 조언 (예: 제육볶음 비유, "자격증은 실력 증명이 아니다")

**추가로 발견한 예외 규칙**: 이 STT 전사본은 품질이 낮아 단순 반복 제거로 안 끝나고 **명백한 오인식**이 섞여 있다 (예: "캐들"→캐글, "통공과"→전공자, "문상관"→수상경력). 문맥상 명확한 오인식은 바로잡아서 인용하고, 어느 부분을 고쳤는지 별도로 밝히지는 않는다(원문 그대로인 척 왜곡하는 것과, 명백한 STT 오타를 고치는 것은 다르다고 판단).

**한계**: 잡음이 심해 문장 자체가 복원 불가능한 구간은 원문 인용을 포기하고 요약본 기준 paraphrase로 대체한다 (예: 09-02 "try/except 마인드셋" 구간). 이 경우 출처 줄에 "(요약본 기준 정리)"라고 표시한다.

**미확정 (사용자가 추가 기준을 줄 수 있음)**: "중요함"의 최종 판단 기준은 위 3가지 외에 사용자가 직접 표시해주는 방식으로 보강될 수 있음. 이 문서의 "5. 원문 인용 기준" 섹션은 계속 갱신 대상.

## 14. 녹취록 커버리지 검증 — 표준 절차 (2026-09-07 도입)

**배경**: 강의안 슬라이드/노트북 구조 위주로 정리하다 보면, 슬라이드에 걸리지 않는 발화(잡담, 부연설명, 실무 팁 등)가 누락되기 쉽다. "강의안에 녹취 시간대를 미리 주석으로 달아두면 누락이 줄지 않을까"라는 아이디어가 나왔으나, 수작업 부담이 크고 근본 원인(슬라이드 위주로 정리하다 보니 슬라이드 밖 발화를 놓침)을 직접 해결하지 못한다고 판단해 채택하지 않음. 대신 아래처럼 **정리 마지막 단계에 원문 전체를 다시 훑는 검증 패스**를 표준 절차로 추가함.

**절차**:
1. 날짜별 기술 페이지 + 커리어 허브 반영분까지 초안을 다 작성한 뒤, 그날 녹취록 원문(`transcripts/YYYYMMDD_N.txt`)을 처음부터 끝까지 다시 훑는다. ("다음 계획" 섹션을 적기 전, 즉 페이지를 마무리하기 직전에 수행한다.)
2. 문단/발화 단위로 "이 내용이 최종 정리본 어디에 반영됐는가"를 확인한다 — 기술 페이지의 특정 섹션인지, 커리어 허브의 특정 섹션인지, 아니면 의도적으로 뺀 잡담/반복인지.
3. 반영이 안 된 내용을 발견하면: (a) 기술적으로 유의미하면 해당 날짜 기술 페이지에 섹션을 추가하고, (b) 실무/커리어성이면 커리어 허브에 섹션을 추가하고, (c) 사소한 반복·잡담이면 의도적 제외로 판단하고 넘어간다.
4. 이 검증 패스를 거쳤다는 사실과 결과(누락 발견 여부)를 이 기준서의 해당 날짜 작업 기록에 한 줄로 남긴다.

**한계**: 이 절차는 STT 원문(`transcripts/`)이 있는 날에만 완전하게 적용 가능하다. 원문이 없어 요약본(`summaries/`)만으로 정리한 날은 요약본 자체가 이미 손실을 포함하므로 효과가 제한적이지만, 그래도 요약본 전체를 대상으로 같은 절차(요약본에 있는 내용이 정리본에 다 반영됐는지 확인)를 수행한다. 녹취본 자체가 없는 날(예: 09-02 Data Scaling)은 적용 대상이 아니다.

> 아래 underfitting / overfitting 그래프 가장 중요 / underfitting : 퀄리티 있는 feature를 많이 만들기 (지금 경진대회 기준 20~30개) / test 와 train score 차이가 적은 구간을 찾으면 그때부터 하이퍼 파라미터 조작

그 밖에 살린 주석: `shape → (row=500, columns=2) → (평가 데이터 수, class별 확률)`, `roc = fpr & tpr 의 면적이 auc`, `전체 데이터 수가 아니라 가장 작은 class의 수를 기준으로 판단`, `자체 경진대회에 가장 효과적`(SMOTE 위).

### 넣은 이미지 6장

| 그림 | 대응하는 강의 발언 |
|---|---|
| 오버/언더피팅 이론 곡선 | 사용자가 "가장 중요"라고 주석 단 그 그림 |
| 25차 다항 모델 | "학습 데이터를 다 지나가니까 100점을 받는 거예요" |
| Training/Testing error 실측 곡선 | "어느 시점부터 test는 올라가고 train은 내려가며 격차가 벌어진다" — 이론 곡선의 실측판이라 **쌍으로** 배치 |
| Balanced(5:5) vs Imbalanced(9:1) 결정경계 | "비율이 깨졌기 때문에 웬만하면 죽었다고 예측한다" |
| RandomUnderSampler 전/후 | 경계는 교정됐지만 데이터가 200→20으로 쪼그라든 게 보임 = 언더피팅 위험 |
| SMOTE 전/후 | 반대로 소수 클래스만 20→200으로 불어남 |

마지막 두 장은 **언더 vs 오버의 트레이드오프를 한 쌍으로** 보여주려고 같은 데이터·같은 축의 그림으로 골랐다 (§19 KNN n=1/n=3과 같은 패턴).

- 44교시 "여러분들의 저 부스팅 계열의 피처 임포턴스는 (…) **신뢰할만한 데이터가 아니라는 뜻이에요.** (…) 바로 샤프예요"

### XAI 페이지의 핵심은 "그래프 읽는 법"이었다

강의안 `6. XAI.ipynb`의 마크다운은 `summary_plot` 설명이 두 줄뿐이다. 그런데 녹취 44교시에는 **판단 기준이 통째로** 들어 있었다:

- 색이 깨끗이 분리 → 좋은 피처, **방향(좌/우)은 상관없다**
- 색이 섞임 → 경향성 없음 → **버리는 게 아니라 새 피처를 만들라는 신호** ("EDA가 부족하다는 뜻")
- 이미 잘 분리된 건 **그만 건드린다** (오버피팅)
- bar보다 beeswarm — bar는 다시 수치형(age·fare)이 위로 올라간다

이게 이번 정리에서 가장 값어치 있는 부분이라 **표 + 인용 + 실제 그래프 3장**을 한 섹션(§4)에 몰아넣었다. `dependence_plot`(§5)은 그 흐름의 후속(섞인 피처 → 확대 → 어린이 구간 발견 → 새 피처)으로 배치했다.

### 이미지 처리

`extract_all.py`로 두 노트북에서 HPO 8장 / XAI 21장을 뽑았고, **그중 10장만 올렸다.** 기준:

- 개념 도식(Grid/Random 격자, SHAP vs SAGE) — 글로 설명하기 어려운 것 ✅
- 강사가 화면에서 **직접 해석해준** 결과 그래프(summary_plot, dependence_plot, feature_importance 편향) ✅
- `for col in X_te.columns` 루프가 뱉은 13장(cell044_08~20) — **전부 제외.** 같은 종류 반복이라 대표 1장이면 충분하다
- 히트맵(cell040/056) — 강의안 결론("criterion은 영향 없다")이 한 줄로 요약되므로 텍스트로 대체

**캡션은 이미지를 실제로 열어보고 썼다.** cell058은 이름이 `best_cumulative_score`라 "높을수록 좋음"으로 오해하기 쉬운데, 코드를 보니 `.cummin()`(누적 **최솟값**)이었다. 파일명·변수명만 보고 캡션을 쓰면 틀린다 — **코드 셀을 같이 확인할 것.**

### 페이지 제목 규칙을 뒤늦게 맞췄다

처음에 `🎛️ 하이퍼파라미터 튜닝 (…)`처럼 이모지+주제로 만들었다가, 그룹 안의 다른 페이지가 전부 `2026-09-10 …정리` 형식이어서 **`update_properties`로 제목만 바꿨다**(아이콘은 유지). 페이지 ID·URL은 그대로다.

→ **새 페이지를 만들기 전에 부모 그룹을 `notion-fetch`해서 형제 페이지 제목 형식을 먼저 볼 것.** 상시 참고 노트(🧱 모듈화)만 이모지+주제 형식이고, 날짜 페이지는 `YYYY-MM-DD 주제 정리`다.

### 모듈화 노트에 추가한 두 조각

날짜 페이지가 아니라 🧱 모듈화 노트로 보낸 것들:

| 위치 | 내용 | 왜 여기인가 |
|---|---|---|
| §0-1 재현성 | 43교시 "모듈화가 선택이 아니에요" — 주최 측이 코드를 재실행해 **소수점 0.00001만 달라도 박탈**. 시드 고정을 전 함수에 걸어야 한다 | §0(왜 모듈화인가)의 가장 강한 근거. §4 데코레이터와 직접 연결된다 |
| §8-1 주피터 파일 관리 | 44교시 "5번 제출했으면 주피터 파일 5개는 나와야 돼요" + 과거 1등 사례 **"모듈화는 너무 잘했는데 주피터 파일을 관리를 못했다"** | 모듈만으로는 재현이 안 된다는 지적. §5(파일 나누기)의 짝 |

→ **모듈화 노트는 계속 이렇게 키운다.** 날짜 페이지에는 그날의 기술 내용만 두고, "언제 다시 봐도 유효한 작업 규율"은 이쪽으로 뺀다.

## 32. 2026-09-11 — 날짜 페이지를 데이터베이스로 전환 (태그 도입)

### 왜 했나

사용자 질문: "노션에 검색 기능이 있긴 있는데, 태그 기능이 있다면 태그를 쓰는 게 좋을까?"

**핵심 사실 하나가 답을 결정했다** — Notion에서 태그(multi-select)는 데이터베이스 행에만 존재한다. 일반 하위 페이지는 속성이 제목뿐이다. 그래서 "태그를 쓸까"는 사실상 "DB로 바꿀까"였고, 그 사실을 먼저 알려준 게 이 대화에서 가장 쓸모 있는 부분이었다.

### 검색 vs 태그 — 어떻게 설명했나

검색이 **되는** 경우와 **안 되는** 경우를 갈라서 보여줬다.

- 잘 됨: "랜덤 서치" 같은 고유 키워드
- 안 됨: "평가지표가 나온 페이지 전부" — 페이지마다 표현이 달라 한 번에 안 잡힌다. 검색은 **추측**을 주고 태그는 **확정된 목록**을 준다. 복습용으로는 후자가 필요하다.

### 09-10 그룹 구조로 이미 해결된 것은 세지 않았다

전날 만든 그룹 5개가 사이드바 문제를 이미 해결했으므로, 태그가 **추가로** 벌어주는 것만 근거로 삼았다 — 한 페이지가 여러 주제에 걸치는 경우다. 부모는 하나뿐이지만 태그는 여럿이다.

### 마이그레이션 순서 (그대로 재현 가능)

1. `notion-create-database` — 허브 밑에 `📚 강의 노트`, SQL DDL로 스키마 한 번에
2. `notion-move-pages` — 28개를 `data_source_id` 부모로 이동. **ID·URL 유지되어 기존 관련 노트 링크가 안 깨진다**
3. `notion-update-page` × 28 — `update_properties`로 날짜·영역·주제·강의안 채우기 (7개씩 병렬)
4. `notion-create-view` × 4
5. 허브 본문 정리 + 기준서 갱신

### 겪은 것

- **`앵상블` 오타로 400** — multi-select 값은 정의된 옵션과 정확히 일치해야 한다. §21의 "한글은 손으로 이스케이프하지 말 것" 교훈이 속성 값에도 그대로 적용된다.
- **날짜 키 이름** — `날짜`가 아니라 `date:날짜:start`. Date 속성은 start/end/is_datetime 세 개로 펼쳐진다.
- **제목은 안 건드렸다.** `2026-09-10 ` 접두사가 `날짜` 속성과 중복이지만, 28개를 고치면 기존 페이지들의 `관련 노트` 링크 표시 텍스트가 어긋난다. 중복을 감수하는 쪽이 싸다.
- **강의안 경로는 `find`로 실제 확인하고 넣었다.** 기억으로 쓰면 틀린다. 확신이 없는 5개(09-04 회귀 2개, 09-07 MLE·분류알고리즘·앙상블)는 **폴더 단위까지만** 적었다 — 틀린 파일명을 적는 것보다 낫다.
- **그룹 페이지 5개는 삭제하지 않았다.** Notion API에 페이지 삭제가 없고, `allow_deleting_content:true`로 우회하는 건 되돌리기 어려운 동작이라 허브에 "🗑️ 삭제 대상" 섹션으로 남기고 사용자에게 넘겼다.

### 태그 설계에서 실제로 지킨 규칙

**영역 경계를 넘지 않는 태그는 만들지 않는다.** 처음에 `크롤링`·`협업·환경` 같은 걸 넣을까 고민했는데, 이건 영역 하나 안에서만 쓰여서 영역과 중복이다. 결국 남긴 건 `크롤링`(환경설정 그룹 안 3개를 묶는 실용성) 정도이고, 나머지는 전부 두 개 이상 영역에 걸친다.

**빈 태그를 억지로 채우지 않았다** — `2026-09-02 머신러닝 개요`는 개요라서 걸리는 주제가 없다. 없으면 비운다.

### 다음에 이런 요청이 오면

- 구조 변경 제안 전에 **"지금 병목이 무엇인가"를 먼저 확인한다.** 이번엔 사용자가 찾기 어렵다고 한 적이 없어서, 태그의 이득을 과장하지 않고 "쓰면 좋지만 지금 병목은 아니다, 다만 28개일 때가 제일 싸다"로 정리했다.
- 마이그레이션 비용은 **항목 수에 비례**한다. 할 거면 일찍.

## 33. 2026-09-11 — 28개 페이지 전부에 `관련 노트` 링크 심기

DB 태그가 "같은 주제다"까지 말해준다면, 이건 **"왜 연결되는가"**를 남기는 작업이다. §32에서 "태그가 대체 못 하는 것"이라고 적어둔 그 부분을 실제로 채웠다.

### 형식 (28장 공통)

```markdown
---

### 🔗 관련 노트

- <mention-page url="https://app.notion.com/p/<id>"/> — 왜 연결되는지 한 줄
- ...

📚 전체 목록·주제 태그로 찾기 → [강의 노트 DB](https://app.notion.com/p/e92ee1d3029046ae8da54182226aef85)
```

**`<mention-page url="..."/>` 를 쓴다.** 마크다운 링크 `[제목](url)`도 되지만, mention은 **페이지 제목이 바뀌면 표시도 따라 바뀐다.** 제목을 손볼 여지가 있는 KB에서는 mention이 맞다. 기존 페이지들이 이미 이 형식을 쓰고 있었다(09-10 교차검증의 모듈화 노트 링크).

한 줄로 검증하고(교차검증 페이지) 나머지를 5~6장씩 병렬로 붙였다.

### 링크를 고른 기준

**"이 페이지를 보다가 막히면 어디로 가야 하는가"** 한 가지만 봤다. 태그가 같다고 다 걸지 않았다 — 그러면 태그 필터의 복사본이 될 뿐이다.

세 종류만 남겼다.

| 종류 | 예 |
|---|---|
| **선행 / 후속** | 09-04 선형회귀 → 09-04 다중회귀&규제 → 09-09 오버피팅 |
| **짝을 이루는 것** | 09-02 인코딩 ↔ 09-02 스케일링 (같은 Enum+fit/transform 패턴) |
| **나중에 뒤집히는 것** | 09-07 부스팅 → 09-10 XAI (**"이 페이지의 feature_importance는 믿지 마라"**) |

세 번째가 제일 값어치 있다. 시간순으로 배운 내용이 **나중 강의에서 반박되는 지점**은 검색으로도 태그로도 절대 안 잡힌다. 09-07 부스팅 페이지를 몇 주 뒤에 열었을 때 그 경고가 거기 있어야 한다.

### 양방향으로 걸었다

A→B를 걸면 B→A도 걸었다. 특히 09-10 XAI·HPO 두 장은 어제 만들 때 앞쪽 페이지를 안 걸어놨어서, 이번에 09-07 부스팅·09-02 전처리·09-01 EDA를 역방향으로 추가했다.

> `mention-page`는 Notion UI의 backlink에 자동으로 잡히므로 **엄밀히는 양방향이 자동**이다. 그래도 본문에 직접 쓴 이유는 backlink에는 "왜"가 없기 때문이다.

### 잘 뽑힌 연결 몇 개

- **08-31 Seaborn → 09-10 XAI** — 날짜로는 10일 떨어져 있지만 결국 같은 능력이다: **그래프를 읽어서 다음 행동을 정하는 것**
- **09-02 인코딩 → 09-10 XAI** — 원핫 0/1 컬럼이 `feature_importance`에서 불리하게 나오는 이유가 인코딩 방식에 있다
- **09-02 스케일링 → 09-08 차원축소** — PCA는 분산 기준이라 스케일링이 선행 필수
- **09-01 EDA ↔ 09-10 XAI** — summary_plot에서 색이 섞인 피처 = "EDA가 아직 부족한 곳"

### 한계 (정직하게)

08월 페이지 일부는 **본문을 다시 읽지 않고 제목·주제 태그·커리큘럼 순서만으로** 링크를 걸었다. 제목이 워낙 서술적이라(`분류 알고리즘(로지스틱·SVM·트리·KNN) & 앙상블(배깅·부스팅)`) 관계 자체는 틀릴 수 없지만, **"§6에서 말한 그것"처럼 내부 절 번호를 가리키는 표현은 실제로 읽은 페이지에만** 썼다(09-10 교차검증 등).

### 다음에 이런 요청이 오면

- 새 날짜 페이지를 만들 때 **`관련 노트`를 처음부터 넣는다.** 나중에 몰아서 하면 28장을 다시 훑어야 한다.
- 새 페이지를 만들면 **역방향도 그날 바로** 건다. 앞 페이지에 "이건 나중에 뒤집힌다"를 심을 수 있는 건 그때뿐이다.

## 34. 2026-09-11 — 그룹 페이지를 살려서 linked view로 채움

§32에서 "비었으니 삭제하라"고 넘겼던 그룹 페이지 5개를, 사용자 요청으로 **삭제하지 않고 목록 페이지로 되살렸다.**

### 왜 손으로 링크를 나열하지 않았나

사용자는 "이전처럼 강의 제목 링크를 만들어달라"고 했다. 그대로 `<mention-page>`를 나열해도 되지만, **그러면 새 강의를 만들 때마다 그룹 페이지도 같이 고쳐야 한다.** 그건 §32에서 DB로 옮기며 없앤 수작업이 그대로 돌아오는 것이다.

대신 **linked database view (list 타입)** 를 넣었다.

```
notion-create-view
  parent_page_id   : <그룹 페이지 id>       ← database_id가 아니라 이것
  data_source_id   : collection://102b0c93-...
  type             : list
  configure        : FILTER "영역" = "지도학습"; SORT BY "날짜" ASC; SHOW "날짜", "주제"
```

- `parent_page_id`를 주면 그 페이지 **본문 끝에 inline linked view 블록**이 붙는다 (UI의 `/linked` 명령과 같다)
- `database_id`를 주면 DB 자체에 탭이 하나 더 생긴다 — **둘은 다른 동작이다**
- list 타입은 제목만 세로로 나열해서 **예전 하위 페이지 목록과 겉모습이 거의 같다**

결과: 보기에는 예전 그대로인데, `영역`만 맞게 넣으면 새 강의가 **자동으로** 그 그룹에 나타난다.

### 중복은 감수했다

DB에 이미 `🗂️ 영역별` 보드 뷰가 있어서 기능은 겹친다. 그래도 그룹 페이지를 남긴 이유:

1. 사이드바에서 주제로 바로 진입하는 경로가 유지된다
2. **보드 컬럼에는 글을 못 쓴다.** 그룹 페이지에는 소개문("2026-09-08 ~ . 타깃 없이 피처만 다루는 학습 — 차원 축소와 군집화")이 이미 있고, 앞으로 그 주제의 요약·정리를 더 쓸 수 있다

### 허브 정리

`🗑️ 삭제 대상` 섹션을 `📚 주제별 정리`로 되돌렸다. 삭제 안내 문구는 제거.

### 다음에 이런 요청이 오면

**"목록을 만들어달라"는 요청은 대부분 linked view가 정답이다.** 손으로 나열한 목록은 만드는 순간부터 낡기 시작한다. 겉모습이 목록이어야 한다면 list 타입을 쓰면 된다 — 태그를 보여주고 싶으면 `SHOW`에 넣는다.

### 34-1. 태그가 제목을 밀어낼 때 — 리스트는 한 줄 고정이다

사용자 피드백: "태그가 많아지니까 제목이 많이 가리는데, 제목을 아래 줄로 내려서 두 줄로 표현해줄 수 있을까?"

**리스트 뷰는 한 줄 고정이고 줄바꿈 옵션이 없다.** `notion://docs/view-dsl-spec`을 확인한 결과 `WRAP CELLS`는 **table 전용**이고, list/gallery에는 카드 크기·줄 수를 정하는 지시어가 아예 없다.

| 뷰 타입 | 제목과 속성의 배치 |
|---|---|
| list | **한 줄.** `SHOW` 순서대로 가로 나열 → 태그가 많으면 제목이 잘린다 |
| table | 열로 분리. `WRAP CELLS true`로 셀 안에서 줄바꿈 가능 |
| **gallery** | **카드. 제목이 위, 속성이 아래로 쌓인다** ← 두 줄을 원하면 이것 |
| board | gallery와 같은 카드지만 `GROUP BY` 필수 |

그래서 그룹 페이지 5개에 **gallery 뷰**를 새로 만들었다.

```
type      : gallery
configure : FILTER "영역" = "<값>"; SORT BY "날짜" ASC; SHOW "제목", "주제"
```

**`날짜`는 SHOW에서 뺐다** — 제목이 이미 `2026-09-04 …`로 시작하므로 순수 중복이다. 정렬은 `SORT BY "날짜"`로 그대로 동작한다(표시하지 않아도 정렬은 된다).

### ⚠️ 뷰는 API로 삭제할 수 없다

`notion-update-view`에는 type을 바꾸는 기능이 없고(name·filter·sort·display만), 뷰를 지우는 도구도 없다. 그래서 **기존 list 뷰 블록이 그대로 남는다.** 사용자가 직접 지워야 한다.

→ **뷰 타입은 만들기 전에 정할 것.** 바꾸려면 새로 만들고 옛것을 손으로 지우는 수밖에 없다.

남은 list 뷰도 `SHOW "제목", "주제"`로 같이 고쳐뒀다(제목 우선·날짜 제거). 둘 중 무엇을 남겨도 보기 괜찮게.

### 렌더링은 확인하지 못했다

MCP로는 뷰 설정 JSON만 돌아오고 **실제 화면은 볼 수 없다.** "갤러리가 두 줄로 보인다"는 Notion의 카드 구조에 근거한 것이지 내가 눈으로 확인한 게 아니다. 레이아웃 요청은 항상 사용자 확인을 받을 것.

`3-1`, `3-2` 두 노트북 모두 **모델·옵티마이저·EarlyStopper가 fold 루프 *바깥*에서 1회만 생성**된다.
→ 같은 모델이 fold를 넘어 학습을 이어가므로, fold N의 "검증" 데이터는 fold 1~N-1에서 **이미 학습에 쓴 데이터**다.

**증거는 숫자에 있었다** (fold별 best val loss가 단조 감소 → 누수의 전형):
```

아이폰: 0.7228 → 0.2683 → 0.1308 → 0.0684 → 0.0280
```
| | 마지막 fold 검증 | 홀드아웃 테스트 |
|---|---|---|
| 네이버 리뷰 | 0.987 | **0.7375** |
| 아이폰 리뷰 | 0.994 | **0.8705** |

**강사는 이 현상을 "K-Fold가 로컬 미니마를 극복했다"로 해석하고 "경진대회에서 K-Fold는 필수"라고 강조했다.**
→ 결론은 맞지만 **근거로 든 이 로그는 K-Fold의 효과가 아니다.** 노트에 양쪽을 다 적고, 고친 코드(fold 안에서 모델 재생성 + fold별 저장 경로 + `평균 ± 표준편차` 보고)를 실었다.

**교훈: fold 성적이 단조 감소하면 모델 생성 위치를 먼저 본다.** 정상적인 K-Fold는 fold 성적이 서로 비슷하다.

## §50. 2026-10-02 자동화 루프 검증 — 중간 스냅샷을 최종본으로 오인하지 않기

### 발생한 일

`claude_input_20261002.md`를 기준으로 1차 정리를 진행했을 때,
실습 노트북이 수업 중 작성·수정 중인 상태였는데도 일부 코드 지적이

이후 더 완성된 노트북을 다시 받아 같은 날짜를 재실행하자 다음이 확인됐다.

- 1차에서 없다고 판단했던 코드가 완성본에는 존재한 사례가 있었다.
- 반대로 완성본에서도 유지되는 지적도 있었다.
- 같은 날 수업 녹취 파일도 계속 추가되고 있었다.
- 강사는 수업 중 노트북을 직접 실행하면서 문제를 찾고 수정하고 있었다.

즉 **같은 날짜 = 같은 입력 상태가 아니었다.**

### 새 운영 규칙

1. **수업 중 생성한 `claude_input`은 중간 스냅샷으로 본다.**
2. 녹취가 계속 추가되거나 노트북 최종 여부가 불명확하면
   코드 문제를 `결함`으로 확정하지 않고 **`재검증 필요`** 로 둔다.
3. 수업 종료 후 최종 노트북이 확인되면 같은 날짜 자료를 다시 생성한다.
4. 재실행 시 이전 지적을 단순 누적하지 않고 다음으로 재분류한다.
   - 해결
   - 유지
   - 새 발견
   - 강사 의도
   - 확인 필요
5. 이전 입력의 오판은 새 최종 정리에 그대로 남기지 않는다.

## §51. 2026-10-02 최종 자동화 루프 검수 — 근거 비교·진단 순서 보강

### 1. 강의안 대응본과 줄 단위로 대조한다

`reset_seed`의 numpy 누락은 실습 노트만 봤을 때는 일반적인 누락처럼 보였지만,
강의안의 `reset_seeds`와 직접 대조하자 **강의안에 있던 한 줄이 빠진 것**으로 확정됐다.

앞으로 실습 노트의 함수가 강의안에 대응본이 있으면 **줄 단위로 대조한다.**

- 누락된 한 줄이 실제 결함일 수 있다. 예: `np.random.seed(seed)`
- 반대로 실습 노트에만 추가된 한 줄은 의도적 개선일 수 있다. 예: `torch.backends.cudnn.benchmark = False`
- 대응본을 비교하지 않으면 결함인지 스타일 차이인지 구분하기 어렵다.

### 2. `강사 의도`와 `강사 관행`을 구분한다

기존 분류인 `해결 / 유지 / 새 발견 / 강사 의도 / 확인 필요`만으로는
강사가 말로 설명하지 않았지만 강의안 코드에서 반복되는 패턴을 분류하기 어려웠다.

앞으로 다음 두 항목을 구분한다.

- **강사 의도**: 녹취의 발화로 설계 이유가 확인된 경우
- **강사 관행**: 발화는 없지만 강의안 코드에서도 같은 방식이 확인된 경우

`강사 관행`은 필요하면
**교육용 단순화로는 합리적이지만 실무 기준에서는 다를 수 있음**을 함께 적는다.

### 3. STT 환각은 줄 전체 삭제보다 접두부 제거를 우선한다

145교시 `00:05:47`처럼 무음 구간 환각 용어 나열 뒤에 실제 발화가 이어 붙는 사례가 있었다.

따라서 교정본에 용어집 나열·숫자 나열 같은 무음 환각이 보여도
**줄 전체를 자동으로 버리지 않는다.**

- 환각 부분은 인용 후보에서 제외한다.
- 실제 발화가 뒤에 이어지면 환각 접두부만 제거한다.
- 2026-10-02 기준 입력 생성 단계에서 자동 필터링은 적용하지 않고 사용자 판단을 유지한다.

### 4. 학습 문제는 모델보다 계측기를 먼저 확인한다

학습 결과가 이상할 때 모델 구조나 하이퍼파라미터를 먼저 바꾸기 전에
**측정과 기록이 정상인지 먼저 확인한다.**

확인 순서:

1. TensorBoard 등의 x축 증분이 올바른가
2. 시드가 실제 사용 라이브러리에 적용됐는가
3. 스케줄러의 `step()` 호출 단위가 설정 단위와 맞는가
4. 기록값이 평균인지 누적합인지 확인했는가

계측기가 틀리면 그래프를 근거로 한 이후 판단도 신뢰하기 어렵다.

### 5. 설정값의 단위와 호출부의 단위를 비교한다

`CyclicLR` 사례에서는
`step_size_up=len(train_dl)`과 `gamma=0.8**(1/(2*len(train_dl)))`이 배치 단위 호출을 전제로 했지만,
실제 `scheduler.step()`은 에포크 단위로 호출되고 있었다.

앞으로 결함을 검토할 때
**설정값이 가정하는 단위와 실제 호출부의 단위가 같은지** 확인한다.

외부 문서를 보기 전에도 코드 내부의 단위가 서로 모순되면 중요한 검토 신호로 본다.

### 6. `claude_input`에 텍스트 셀 출력 포함을 검토한다

이번 검수에서는 `len(vocab)`, `max_len`, 최종 정확도 같은 실제 출력값이 없어
일부 판단이 추정에 머물렀다.

향후 Archivist 개선 후보:

- Notebook 셀 출력 중 `shape`, `len()`, `print()` 같은 **짧은 텍스트 출력만 포함**
- 이미지 출력 제외
- 장문 로그 제외
- 출력 크기 제한 유지

현재 단계에서는 운영 규칙으로만 기록하고 코드 수정은 별도 검토한다.

### 7. 본문 근거 비중과 예외

최종 기준은 다음 비중으로 본다.

- **실습 노트 코드 65%**
- **강의안 20%**
- **녹취 15%**

다만 단순 비중만으로 판단하지 않는다.

기술의 현재 구현 상태는 코드를 가장 강하게 보되,
**설계 의도는 녹취에만 존재할 수 있다.**
코드만 보면 결함처럼 보이는 구조도 강사의 발화를 확인하면 의도된 설계일 수 있다.

따라서 결함과 의도를 구분할 때는 녹취 근거를 반드시 확인한다.

## §52. 강사 이야기 이중 보존 — 수업 맥락과 장기 인사이트를 분리한다

### 문제

날짜별 강의 노트의 `강사 이야기`에는 두 종류의 내용이 섞인다.

- 그날 코드·실습·오류 상황을 알아야 의미가 살아나는 설명
- 날짜와 상관없이 나중에 다시 볼 실무·커리어·학습 태도 조언

둘을 전부 날짜 페이지에만 두면 장기 인사이트가 묻히고,
반대로 전부 커리어 허브로 옮기면 **왜 그 말이 나왔는지 수업 맥락이 끊긴다.**

### 원칙

앞으로 강사 이야기는 `한 곳만 선택`하지 않고 다음 두 질문으로 판단한다.

1. **왜 이 말이 나왔는지 알려면 그날 수업 맥락이 필요한가?**
   - Yes → 날짜 페이지에 남긴다.
2. **6개월 뒤 기술 내용 없이 읽어도 다시 쓸 가치가 있는가?**
   - Yes → `커리어 & 실무 인사이트` 허브에도 보낸다.

둘 다 Yes면 **이중 보존**한다.

### 두 곳의 역할

- **날짜 페이지**: 그날의 코드·실습·오류·디버깅과 연결해 `왜 이 말이 나왔는가`를 보존
- **커리어 허브**: 날짜와 무관하게 재사용할 수 있도록 `이 조언을 앞으로 어떻게 쓸 것인가` 중심으로 정리

같은 문장을 그대로 복제하지 않는다.
날짜 페이지는 맥락 중심, 허브는 주제 중심으로 쓴다.

### 링크 규칙

이중 보존한 항목은 양방향 연결한다.

- 날짜 페이지 → 해당 커리어/실무 인사이트 페이지
- 커리어/실무 인사이트 페이지 → 원래 날짜별 강의 노트

허브 쪽에는 반드시 다음 형식을 남긴다.

`출처: YYYY-MM-DD OO 강의 중`

### 2026-10-02 적용 예

- `수치가 안 좋을 때 — 왜 그런지, 어떻게 할지 말할 수 있어야 한다`
  - 실제 모델 디버깅과 직접 연결되므로 날짜 페이지 본문 유지
  - 동시에 `실무 개발 습관 · 마인드셋`에 일반화된 실무 문제해결 원칙으로 재정리 가능
- `AI와 싸우지 말고 소통하라`
  - 날짜 페이지에는 짧은 맥락과 허브 링크만 남겨도 됨
  - 본문은 `실무 개발 습관 · 마인드셋`이 주 목적지
- `코딩 어린이는 판단하지 말고 일단 가져가라`
  - 학습 태도 조언이므로 허브 중심
  - 그날 도구·기술 선택 맥락이 필요하면 날짜 페이지에 요약 유지
- `코딩은 실력이 올라가면 생각한 대로 된다`
  - 기술 맥락 의존도가 낮으므로 허브 중심

### Claude C 출력의 의미

앞으로 `C. 커리어 허브 반영분`은 `강사 이야기 복사본`이 아니다.
날짜 페이지에서 발견한 발언 중 **장기적으로 재사용할 가치가 있는 인사이트를 승격하는 단계**다.

각 C 후보에는 다음 판단을 포함한다.

- 수업 맥락 보존 필요 여부
- 독립 재사용 가치 여부
- 날짜 페이지 처리 방식
- 허브 반영 목적지
- 양방향 링크 후보

## §53. 2026-10-07 (158~168교시) LSTM·GRU 시계열 — 측정으로 결함을 확정한 날

> 작성 2026-10-08 · 입력 `claude_input_20261007.md` (239,640B / 4,215줄) · 산출물 `claude_output_20261007.md`
> Notion 반영: 날짜 페이지 신규 1건, 커리어 허브 3건, 상시 참고 2건 추가 + 1건 신설, 역방향 링크 5건

### 53-1. 파일명에 시각이 붙은 녹음은 같은 교시의 두 번째 테이크다

`auto_YYYYMMDD_N_HHMM.wav`는 **N교시를 HH:MM에 다시 시작한 것**이다. 10-07에 처음 나왔다(`auto_20261007_1_0933.wav`). 앱의 파일명 분리 기능이 실제로 작동한 결과다 — 이전 코드였다면 앞 27분을 덮어썼다.

- 교시 매핑 시 접미사를 먼저 확인한다. `_1`과 `_1_0933`은 같은 1교시다.
- 두 녹취가 **문장 단위로 이어지는지**로 전반/후반을 확정한다(`163` 끝 "셀이라고 하는 친구가 무슨 친구냐" ↔ `158` 첫머리 "셀과 히든 스테이트는 같은 데이터").
- 두 파일 사이의 시간 차가 **녹취 공백**이다(09:27~09:33, 6분). 자료 상태에 적는다.
- → 규칙 §1에 반영

### 53-2. `transcripts/old/`에 있는 파일은 자동화 입력에서 빠진다

정리를 마친 녹취를 `old/`로 옮기는 운영 방식과 `claude_input` 생성이 충돌한다. 10-07의 `164`가 실제로 입력에 없었다.

- 이번은 **의도한 제외**였다 — 강의가 아니라 토이프로젝트 기획 미팅(수동 녹음 13:43~14:03)이었다.
- 그러나 **당일 녹취를 실수로 옮기면 조용히 누락된다.** 입력에 없는 것과 존재하지 않는 것을 구분할 수 없다.
- 대응: 정리 전에 `transcripts/`와 `old/`를 **함께** 확인한다.
- → 규칙 §1 자료 소스 표와 §9 체크리스트에 반영

### 53-3. 강의안 mtime이 수업일보다 앞서면 실시간 코드는 강의안에 없다

`4-2`·`4-3`은 09-28 15:06 이후 수정되지 않았고 `course/` 사본과 **바이트 수까지 같았다.** 즉 강사가 수업 중 친 코드는 강의안에 반영되지 않았다.

- 판정 방법: `study/`와 `course/`의 같은 파일을 **크기와 mtime으로 비교**한다. 동일하면 "배포본 그대로"다.
- 그 경우 수업 중 코드는 **녹취 + 개인노트로만 복원된다.** 강의안의 저장된 출력은 **그날 화면이 아니다.**
- 실제로 강의안은 2024년 데이터(244행), 수업은 2025-10~2026-10(242행)으로 **데이터가 달랐다.**
- → 규칙 §1 "강의안 찾는 순서"에 반영

### 53-4. 저장된 셀 출력의 반복 횟수가 루프 구조를 증명한다

`tqdm` 진행바는 실행마다 한 줄씩 남는다. 그 **개수를 세면** 루프가 몇 번 돌았는지 알 수 있다.

- 🟠③: 2~5폴드에 `train_step 0/6`이 **각 1회만** → 1에폭 후 중단 확정
- 🟠①: `train_step 0/6` + `test_step 0/2` → train 윈도 179개 / valid 35개 → **섞인 193행에서 윈도를 만들었다** 확정
- loss 값이 없어도 **구조는 증명된다.** 추측으로 적을 필요가 없다.
- → 규칙 §11에 반영

### 53-5. 소수점 끝까지 같은 지표값은 상태 객체 공유의 지문이다

강의안 `4-2`의 저장된 출력에서 `Cross Validation:1~4 >> best loss: 0.003794223885051906` — 네 폴드가 18자리까지 같았다.

- 폴드마다 데이터가 다르면 지표가 같을 수 없다. **같다면 그 값을 들고 있는 객체가 공유된 것**이다.
- 함께 볼 것: 모델·옵티마이저·EarlyStopper가 루프 **밖**에 있는지.
- 반대 지문도 있다. **CV 점수가 비정상적으로 높은데 홀드아웃이 낮으면**(`4-3` 예제1의 ACC 1.0 vs 0.68) 폴드 간 모델 재사용으로 뒤쪽 검증 데이터가 이미 학습된 것이다.
- → 규칙 §11에 반영 (기존 "fold 성적이 단조 감소하면" 항목과 짝)

### 53-6. 녹취의 고유명사가 코드의 문자열 인자일 수 있다

녹취 전체에 "네이버 데이터"가 반복되지만, 코드는 `web.DataReader("005930", "naver", ...)`이고 종목은 **삼성전자**다. `"naver"`는 데이터 소스였다.

- 녹취의 회사명·서비스명은 **대상이 아니라 도구일 수 있다.**
- 확인 순서: 녹취에 나온 이름을 **코드에서 문자열로 검색**한다. 함수 인자 자리에 있으면 도구다.
- 사용자 개인노트의 주석(`# 네이버 주식 값이 리턴`)도 같은 혼동을 담고 있었다. **노트 주석도 녹취와 같은 오류를 물려받는다.**
- → 규칙 §1 "🔴 소스를 추정하지 말 것"에 반영

### 53-7. "강사 관행" 분류가 또 필요했다 — 두 번째

🟠③(EarlyStopper가 폴드 밖)은 사용자가 새로 만든 결함이 아니다. **강의안이 같은 구조이고, 강의안의 저장된 출력이 같은 증상을 보인다.**

- 매니저 문서의 5분류(`해결`/`유지`/`새 발견`/`강사 의도`/`확인 필요`)에는 **"강사 관행"이 없었다.**
- `강사 의도`와 다르다. 의도는 강사가 설명한 것이고, 관행은 **설명 없이 강의안에 들어 있는 패턴**이다.
- 10-02(어휘집을 분할 전에 만든 것)에 이어 **두 번째**다.
- 분류했을 때 달라지는 것: 🟠로 적되 **"내가 틀린 것"이 아니라 "강의안과 함께 고칠 것"**으로 표현이 바뀐다.
- → `claude_notion_knowledge_manager.md` §0에 `강사 관행` 추가 (반영 완료)

### 53-8. 입력 파일에 셀 출력이 없다 — 세 번째

§50(10-02), 10-06에 이어 또다. 이번에는 **점검 결과 세 건(🟠①②③)이 전부 셀 출력에서만 확인됐다.**

- 🟠②: `torchinfo`의 shape 두 줄 (`[10,32,256]` vs `[32,128]`)
- 🟠③: 진행바 개수와 `best score` 네 줄
- 🟠①: 폴드별 배치 수
- 입력만으로는 **전부 "가능성"으로만 적을 수 있었다.** 매번 노트북 원본을 다시 파싱하고 있다.

### 53-9. 하루에 노트북 두 권을 다루면 주제 태그가 늘어난다

10-07은 시계열 회귀(`4-2`)와 자연어 생성(`4-3`)을 같이 다뤘다. 주제 태그가 5개가 됐다(10-06은 3개).

- 태그가 5개를 넘어가면 **페이지를 둘로 쪼갤지** 먼저 검토한다.
- → 규칙 §7에 반영
